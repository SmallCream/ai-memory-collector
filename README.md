# AI Memory Collector

把 AI 对话保存到自己的电脑，并同步到自己的私有 GitHub 仓库。无需安装 Git、本地桥接程序或自建服务，也不需要模型 API Key。

**当前开发版本：0.3.13。** 支持桌面 Chrome / Edge 的 ChatGPT 网页端，提供账号隔离、初始化与定时采集、图片归档、GitHub LFS 同步和新设备恢复。消息数组归档支持游标分页与尾部增量，已有消息树仍完整读取以保留分支。本版修复请求超时被误报为 `INVALID_RESPONSE / SCRIPT_ENVELOPE_INVALID`：浏览器原生取消异常的数字错误码不再进入采集协议，超时正确进入原有有限重试。单次详情请求上限由 20 秒调整为 60 秒，账号核验与列表仍为 20 秒；尚未在用户设备验证本次失败对话能否成功，详见 [验证记录](docs/validation.md)。

## 使用流程

1. 打开并登录 ChatGPT，切换到个人空间。
2. 点击扩展图标，按首次引导授权 ChatGPT、确认账号名称、选择固定保存目录。
3. 可选：连接自己的**私有数据仓库**，填写仅授权该仓库 Contents 读写权限的 GitHub Token。启用后会上传本地归档，也会定时恢复仓库中**各账号**已有归档与图片到本地。默认启用“图片同步到 GitHub（LFS）”，验证保存时单独申请 GitHub 文件传输域名权限；也可以先仅保存在电脑。
4. 完成引导并开始初始化采集。之后在 ChatGPT 页面边缘展开面板即可使用，GitHub 配置留在设置中。

| 方式 | 行为 |
| --- | --- |
| 初始化采集 | 首次遍历普通列表，读取详情并保存；未完成部分保留进度 |
| 定时增量 | 默认每 30 分钟检查新增、更新与待重试项；设置中可改为 15 / 30 / 60 分钟或关闭 |
| 立即检查更新 | 手动触发一次增量检查，无需等待定时任务 |
| 全量补采 | 重新遍历列表并读取详情，补齐缺失文件；同一对话更新原档，不重复建档 |
| 重试失败图片 | 刷新失败图片所在对话的线上详情，逐项补采；不重新扫描对话列表，也不替换已存对话正文 |
| 尝试获取内部附件 | 手动重试已经停止自动获取的内部看图附件，每项尝试一次；仍未取得时继续明确标注缺失 |
| 从 GitHub 恢复 / 补齐图片 | 把已配置私有仓库中的采集器归档和图片恢复到本地，不要求 ChatGPT 登录；保留可重试进度 |

定时采集需要浏览器正在运行、可访问的已登录 ChatGPT 标签页和有效目录权限；已有本地数据的 GitHub 同步与恢复不依赖 ChatGPT 登录。浏览器退出、电脑休眠、登录失效时不保证执行或准点执行；恢复条件后补做检查。同一账号的手动和定时任务共用队列，收起面板不代表暂停任务。

已有采集流程见 [0.2 使用指南](docs/v0.2-guide.md)，0.3 的图片与恢复操作见下文。

## 增量采集的判断

“立即检查更新”和定时采集会分页读取轻量列表中的 ID、标题和更新时间，再决定哪些对话需要详情请求：

| 对话状态 | 本轮处理 |
| --- | --- |
| 新 ID、更新时间变化或标题变化 | 读取该对话详情并更新原档 |
| 已有完整归档，时间及标题相同，JSON / Markdown 均存在且非空 | 跳过详情，不重新写入对话文件 |
| 时间无法识别、归档完整度未确认或文件缺失 | 补采该对话 |
| 上轮读取、保存或加入上传队列尚未成功 | 保留补采义务，连续列表失败也不会将其忘记 |
| 手动“全量补采” | 强制重新读取全部可枚举的对话详情 |

跳过判断不再要求整个账号初始化全部成功，也不因对话处于最近 5 分钟而重复请求。GitHub 恢复后的完整归档可使用清单中的来源更新时间；浏览器索引只在内容哈希与当前清单一致时复用。秒、毫秒、数字字符串和 ISO 时间统一比较；详情若早于列表刚发现的版本则等待重试，不推进成功记录。

列表仍需分页核对，不能只依赖全局“最后同步时间”停止扫描，否则会漏掉较旧但尚未采集的 ID。先按**对话**筛选，再按下述规则读取详情。若平台修改内容却不改变时间和标题，普通列表筛选无法发现，可用“全量补采”复查；已经复用历史前缀的归档还有定期完整复查。日常列表检查只核对本地文件是否存在且非空，不重新计算全部历史正文的哈希。

更新前已经创建的未完成任务仍沿用原队列继续，避免中断文件交付；新筛选规则从下一轮新建检查生效。无需清空数据或重新绑定账号。

## 消息分页与尾部增量

分页读取当前分支的消息数组 `messages` 时，先读取最近一页，使用 `page_info.start_cursor` 作为 `before` 游标向前获取历史；顺序由服务器数组及游标关系决定，不按消息时间自行排序。每页检查 ID、首末游标、分页标记、生成状态及账号；需要拼接时还要求可靠的更新时间和当前节点，多页读取完成后再次核对最新页，发现版本变化则停止本次拼接或回退完整消息树。

| 已有归档 | 处理方式 |
| --- | --- |
| 完整 `messages` 数组，近期已完整核对 | 最新页与本地末尾至少 3 条连续消息的 ID 和脱敏后内容一致，且其后有新 ID，才复用此前的历史前缀 |
| 只遇到一个旧 ID、重叠消息变化、旧 ID 顺序异常或未找到本地末尾 | 继续向前分页，完整读取当前分支；分页不可靠时尝试完整消息树，失败保留原档 |
| 缺失、损坏或未经完整核对的本地归档 | 不作增量基线；缺失时完整补采，人工修改冲突需处理后继续 |
| 已有 `mapping` 消息树 | 继续完整读取消息树，保留历史分支；不会自动转成仅含当前分支的数组 |
| 首次采集或手动全量补采 | 完整读取；新对话优先完整消息树，接口不可用或结构不匹配时尝试完整数组分页 |

仅下载最新一页也会包含少量重叠消息，并非接口只返回“新增的两条”。比较使用与归档一致的脱敏规则，签名凭据变化不作为正文修改；正文、附件身份、状态及原生消息字段的变化仍参与判断。归档继续保存一组完整 JSON / Markdown，不拆成每条消息一个文件，也不伪造消息树节点。

复用前会核对本地 JSON 的哈希，保存尾部合并时再次核对基线版本，防止网络读取期间本地归档已被更新。清单中的 `messageSync` 记录完整读取时间、历史复用方式及消息计数；图片重写和 GitHub 恢复不会把旧历史标成刚刚全量核对。GitHub 冲突处理同样保护已有消息树。

尾部衔接只证明连接处一致，不能证明更早消息未被修改。距离上次完整读取达到 **7 天**或已完成 **20 次尾部增量**，下一轮正常检查会完整读取该对话，即使列表时间未变化也不跳过。它依赖浏览器和账号可用，不是独立常驻任务。手动“全量补采”随时强制完整读取。

当前仅对已有完整数组格式启用尾部增量；旧版数组缺少完整读取记录时先完整读取一次，已有消息树不会因为升级而自动改格式。网站私有分页接口仍需实际账号验收，不保证全部对话都能减少详情下载。

分页中点击暂停，当前请求返回后停止继续翻页，未确认的拼接不写入归档；已开始的文件写入会完成一致的保存与交付记录。继续采集时从当前对话的最新页重新读取，已经完成的其他对话保留。

单次详情 HTTP 请求有 60 秒总时限，覆盖响应头与正文读取，不随数据分块续期；前后账号核验及列表请求各有 20 秒时限。超过时限显示 `TIMEOUT` 并沿用最多 3 次尝试、1 分钟 / 2 分钟退避，未完成响应不落盘。暂停仍在当前采集请求返回或超时后生效；60 秒不是整条长对话多页读取的总时长，也不保证所有慢请求都能完成。

完整消息树中，历史消息可能仍带有 `pending`、`streaming` 或 `in_progress` 状态。采集器只在**同一分支后续**存在 `assistant / finished_successfully / end_turn: true` 的结束消息时，将其作为历史状态原样归档；指向工具或分析通道的消息不作为结束证据。当前分支只能用当前分支的结束记录确认，当前节点或没有结束证据的旁支仍会阻止本次覆盖。不按对话年龄放行，不改写状态，不删除节点；缺页和树结构校验继续执行。消息数组及分页响应暂不使用此例外。

清单中的 `generationState` 记录历史未完成状态与无法确认结束的数量，每次从原生数据重算；Markdown 继续只展示对话。`sourceCompleteness: complete` 表示通过了本次返回结构检查，不表示每条消息都成功生成，也不保证平台全部历史均已取得。升级后可点击“继续采集”重试，无需清空数据。

## 查看运行进度

点击采集进度下方的 **“采集详情”**，或 GitHub／图片区域的 **“下载与上传详情”**，可展开任务情况；轮询刷新会保留展开状态。

- 采集详情：当前正在核验账号、读取列表、读取哪条对话或保存文件，以及队列状态、错误代码和重试时间。
- 本条详情：消息页读取次数、接收消息数、复用历史数、新发现与修改数量；尾部增量明确标注“较早历史未重新核对”。接收数包含重叠及最新页复核，不能当作新增数量。
- 下载与上传详情：当前图片名称、下载／本地保存／LFS 上传步骤、GitHub 对话提交和仓库恢复情况，区分图片已经上传与对话尚未提交。
- 最近结果：保留每类操作最近 20 个步骤，展示最多 50 条队列明细，数量超过时会提示。日志只在本浏览器保存，不同步到数据仓库。
- 等待状态：按实际步骤开始与结束时间显示耗时；请求暂未有新进展、重试退避、采集暂停和上次处理被中断分别说明。计时不代表字节下载进度，也不把等待时间直接判为卡死。

详情采集出现 `INCOMPLETE_DETAIL` 时，展开失败项查看“原因”行和对话 ID。同名对话可以据此区分；原因会说明返回结果中的未完成消息、缺少的树节点引用，或无法核对的分页字段等具体条件。旧记录只有总错误码时，需要在升级后继续采集，才能取得新的原因；不要因此清空已有归档。错误诊断只记录固定原因代码，不记录对话正文、节点 ID、认证信息或原始响应。

采集队列中的 `INVALID_RESPONSE` 表示没有取得符合约定的页面采集结果，不等同于对话内容不完整。0.3.11 会在首次失败后等待 1 分钟、第二次失败后等待 2 分钟，总计最多尝试 3 次；仍失败则保留任务供手动继续。新记录区分主页面结果缺失、脚本执行失败、空返回及返回格式异常。标签页已关闭或离开 ChatGPT 时优先暂停等待恢复；错误返回不会写入归档或推进成功索引。

手动同步等待期间仍刷新只读进度；后台读取迟迟未返回时会提示状态读取等待。重新核验标签页账号时会标明显示的是上次确认账号，核验期间暂禁账号相关操作。更新后的新操作才会产生这些步骤记录，旧历史不会补造。

## 图片与恢复

对话 JSON 继续保存平台原生结构；Markdown 展示对话中的可读内容和图片引用。能够取得的私有／临时图片先保存为本地实体，开启图片同步后通过 GitHub LFS 上传，仓库提交对应指针文件。本地图片、已上传图片、待采集及待上传分别计数，不把链接或指针当成图片已经下载成功。文件以来源实际返回的内容为准，不承诺已核实原始分辨率。

普通对话图片失败时不需要清空数据。展开 **“查看失败原因”**，可看到对话标题、图片名称、错误代码与尝试次数；待处理数量包含失败项。点击 **“重试失败图片”**，会读取对应对话的最新图片来源信息，随后重试现有失败任务。即使对话采集已暂停，也允许这次明确请求的图片补采，每项只尝试一次；采集未暂停时，之后仍按退避时间自动重试。图片已下载但归档入队失败时，只继续交付已有文件，不重复下载。

`asset_pointer_link` 有有效地址时可用于取图；只有 `sediment://` 或失效链接时，会结合归档任务中的文件 ID、对话 ID 尝试文件下载入口。内部接口或 Library 路径可能不适用，补采按钮不保证所有图片都能取得。诊断不会展示下载凭据、签名 URL 或服务器原始响应。

0.3.2 针对 Library 附件下载返回的浏览器不透明跳转，允许浏览器跟随指定的标准下载入口，随后验证最终地址与图片内容。Cookie 限于同源，跨源跳转的 Authorization 由浏览器按 Fetch 标准移除；此例外不用于任意外链或源数据中的其他 URL。

0.3.3 补齐实际观测到的同源 `/backend-api/estuary/content` 下载地址：要求唯一的查询参数 `id` 与当前附件的文件 ID 完全一致，继续核验图片字节和账号。签名地址只临时用于请求，不写进归档或诊断。这个规则用于接收平台返回的地址，不能仅凭文件 ID 构造可用的签名链接，也不代表所有 `ASSET_PENDING` 生成图片已能下载。

0.3.4 增加 `/backend-api/files/download/<文件ID>` 入口，使用任务归属的 `conversation_id`、`download_intent=false`、`inline=true` 获取图片来源。它不要求原图已在当前页面打开，也不使用当前标签页的对话 ID 替代任务归属。请求仍在已登录的同账号 ChatGPT 标签页执行；取得内容后检查原图大小、尺寸、类型、哈希及账号，随后保存本地并进入原有 LFS 队列。旧失败项可直接“重试失败图片”，无需全量重采。该入口已在真实网页资源清单中观测，扩展端到端下载和 LFS 上传仍待用户设备验收。

0.3.5 修正同一图片同时出现在上传附件与 AI 文件引用中的重复计数：只有直接文件引用明确提供文件 ID 与 Library ID 时才合并，保留全部消息来源。旧版多建的 Library 图片任务可在重试时按同账号、同对话的原始记录核对并纠正；原图片已经下载且本地字节验证通过时直接复用。GitHub 合并相同对话原文时应用同样的对应规则，避免旧重复记录重新出现。不能唯一确认对应关系的记录继续保留，不按同名文件猜测。工具运行中产生的附件可能使用另一文件 ID，不能因此判定为同一原图；仍需平台提供可访问的下载来源。

0.3.6 仅将原生消息中 `tool / container.open_image` 的 `execution_output` 附件识别为内部看图附件；同一图片只要还有普通消息引用，就仍按普通图片处理。内部附件也会先尝试下载，仅在下载返回 `HTTP_404` 时停止自动重试，并单独显示 **“内部附件未下载”**。这类记录不再计入普通图片失败数，但不算已下载或完整备份；原始 JSON、文件 ID、消息位置及错误代码继续保留。可点击 **“尝试获取内部附件”** 再试一次；成功取得字节后仍按原流程保存并上传 LFS。401、403、限流或网络失败不按 404 处理；其他工具、用户上传图片、回复展示图片及生成图片不会因文件名或路径相似而被忽略。

旧的 404 任务会在下一次图片任务处理时核对本地原始 JSON 并迁移；暂停采集时也可主动点击“重试失败图片”触发一次尝试。升级、重启、重采及相同原文的 GitHub 合并／恢复会保留经过来源核对的缺失状态，不根据同名或同大小的图片猜测替代关系。

公开外链图片不默认复制到仓库。在设置中主动点击 **“允许检测外链图片”** 后，扩展才申请覆盖 HTTPS 网站的可选权限，并匿名检测外链是否可用；检测不携带 ChatGPT 或 GitHub 凭据。未授权或无法确认的外链保留链接及待处理状态。GitHub 授权不会顺带申请此权限。

在新电脑恢复，或补齐本地缺失图片：

1. 打开扩展设置。首次引导也可以直接点“已有备份？从 GitHub 恢复”，无需先绑定 ChatGPT。
2. 选择保存目录，填写私有仓库、分支和 Token，点“验证并保存”。只手动恢复时可以不勾选“自动同步并补齐本地备份”。
3. 点 **“从 GitHub 恢复 / 补齐图片”**，按提示授权 GitHub 文件传输域名。
4. 查看恢复进度；失败时点“重新尝试恢复”，重新检查仓库并补齐。恢复不会自动启用任何账号的采集，之后采集仍需核实并绑定当前登录账号。

自动同步开启后，也按设置间隔检查远端并补齐各账号的本地归档和图片。恢复只读取采集器识别的账号归档，不是通用 Git 客户端；不会因为远端缺失就删除本地文件。遇到本地手工修改、新旧版本无法判断、图片缺失或权限不足时保留状态，不强行覆盖。图片传输使用 GitHub LFS 的存储与流量额度；是否可用还受 Token、仓库和组织策略影响，界面的仓库连接验证不代表所有图片都已通过实机上传验证。

## 文件与账号

- JSON 保留平台返回的原生对话结构，结构化认证字段会脱敏；Markdown 从同一版本 JSON 自动生成，保留常见富文本与媒体引用，移除可执行 HTML。
- 按网页来源、平台、稳定账号目录隔离写入。目录使用账号标识的哈希，同一账号在不同设备保持一致；自定义名称保留在界面与 account.json，不以同名昵称判断归属。
- 文件名包含创建时间、标题和对话 ID；续聊、改标题或再次补采仍更新原文件路径。
- 本地先保存并核对，再同步到已启用的私有 GitHub 仓库。上传失败保留待同步数据，不显示为上传成功。
- 发现不完整或生成中的详情时保留原档；列表缺失、404 或请求失败不会触发删除。
- 本地人工改动、无法判定的新旧版本和远端竞争会保留数据并提示状态，不强制覆盖。多设备完整恢复仍需进一步验收。

示例目录：

```text
data/web/chatgpt/<稳定账号目录>/
  account.json
  archive/manifest.json
  assets/<图片内容哈希>.png
  conversations/2026/10/
    2026-10-21T06-00-00Z__项目规划__<对话ID>.json
    2026-10-21T06-00-00Z__项目规划__<对话ID>.md
```

图片扩展名按实际内容确定；本地 `assets/` 保存图片字节，GitHub 路径保存 LFS 指针并由对应账号目录中的 `.gitattributes` 标明类型。普通 ZIP 下载可能只包含指针，使用扩展的恢复入口才能补齐已上传的 LFS 图片。

个人对话、Token、Cookie 和登录信息不进入本代码仓库。GitHub Token 只保存在当前浏览器扩展存储中，不传给 AI 网站，也不写入归档。启用 GitHub 同步后会上传**真实对话文件**，启用图片同步后还会上传已取得的私有图片，请使用自己的私有数据仓库。

## 安装与更新

首次安装：取得需要验证的代码版本并解压，在 `chrome://extensions` 或 `edge://extensions` 开启开发者模式，选择“加载已解压的扩展程序”，选中仓库内的 **extension** 文件夹。用户运行插件无需 Node、Python 或 Git。

已有用户请覆盖**原来加载的 extension 路径**，在扩展管理页点“重新加载”，再刷新已打开的 ChatGPT 页面。沿用同一浏览器配置和扩展身份，不卸载重装、不换目录，才能继续使用原扩展存储。

0.1.x 升级会沿用数据库和已保存的目录句柄，迁移仓库、分支及此前明确选择记住的 Token。旧 `p0-captures/` 文件与未保存副本保持原样；首次新版引导仍需确认账号和真实对话上传设置，不会因为曾做过 GitHub 合成文件测试就自动开启上传。

0.2 升级保留账号绑定、采集进度、目录和 GitHub 设置；新增图片同步默认开启，浏览器不会自动授予新增域名权限。需要时在设置中“验证并保存”或点“授权 GitHub 图片传输”，也可以关闭图片同步。旧归档可通过“全量补采”识别图片；过期或已不可访问的源图片不保证可以补回。

0.3.x 升级至 0.3.11 无需清空本地目录、GitHub 数据或扩展存储。原地覆盖代码并重新加载后，支持的消息数组归档会先建立或复用完整基线，再判断尾部增量；消息树继续保留原格式。已有任务可以继续，下一次详情失败会记录具体原因；之前已经标记失败的任务需点击“继续采集”重试。图片失败仍可单独重试。权限范围与数据库名称保持不变。如果本地目录显示“需要授权”，先点击“恢复保存权限”，待状态变为“自动保存”后继续。

Mac 用户可使用 [双击更新器](docs/macos-update.md)。**0.2 之前下载的旧更新器需要一次性替换为新版 `update-macos.command`**：旧脚本只识别带 P0 的扩展名称，新脚本同时接受旧名称和新版名称。保留原 extension 目录，不用卸载插件。更新器只读取 `main`，不会安装尚未合并的开发分支；更新后仍需在扩展管理页重新加载。当前没有浏览器商店版本。

## 当前范围与限制

- 仅接入 ChatGPT 普通对话列表；团队工作区、项目、归档与临时对话尚未完成接入验证。页面昵称和会话身份不代表工作区已验证。
- 网站内部接口不是稳定公开 API。自动优先读取消息树，必要时尝试消息列表；缺少可靠分页结束标记、缺失节点或仍在生成时会提示待补采，不把截断内容当作完整归档。
- 支持可识别的常见栅格图片，单张上限 16 MiB；源平台文件接口、临时链接或权限变化可能导致图片待重试。音频、视频和其他附件保留引用，本版本不保证下载实体。
- GitHub 上传支持读取远端现状、处理提交竞争、保留冲突版本；恢复入口读取归档清单并补齐 LFS 图片，不恢复任意仓库文件或 Git 历史，也不绕过本地冲突。
- 恢复与采集都需要浏览器运行和有效目录授权；中断后保留进度。LFS 上传或下载失败会单独保留待处理状态，不保证单次操作全部完成。
- Gemini、豆包等平台尚未接入。已有平台适配接口，后续需要分别验证账号、列表、详情和消息格式。
- 本阶段只采集归档，不进行 AI 记忆提炼、跨平台注入、搜索展示或自动执行对话中的指令。

## 开发与检查

Node.js 22+，测试使用虚构数据和模拟浏览器/文件/GitHub 接口，不需要用户账号或 Token：

```sh
npm test
npm run check
npm run package
```

打包需要 Python 3，仅收录 `extension/`，输出到 `dist/`。更新器测试还需要 Bash、ZIP、unzip、shasum 等工具；Linux 测试会模拟 macOS 专有命令。CI 执行自动化测试、静态检查和打包。
