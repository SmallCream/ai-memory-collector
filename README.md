# AI Memory Collector

把 AI 对话、图片和附件备份到自己的电脑。GitHub 是可选备份目标；只使用本地保存也能完成配置。无需安装 Git、本地桥接程序或自建服务，也不需要模型 API Key。

**当前开发版本：0.4.8。** 在 ChatGPT 基础上新增豆包网页端适配，按平台和账号分别归档。豆包已完成账号识别、列表分页及正文实际落盘；0.4.1 补齐旧格式图片解析并已实测图片下载；0.4.2 修正已上传图片和历史中断记录导致的详情误判，0.4.3 补齐旧格式空中断记录，0.4.4 增加附件签名地址刷新和 PowerShell 文本归档，0.4.5 将单附件上限提高到 32 MiB，0.4.6 修复豆包未变化对话仍重复读取正文的问题，0.4.7 新增“停止本轮”，0.4.8 减少空闲账号核验。GitHub 仅备份对话 JSON、Markdown 和清单；附件继续保存在本地。升级保留原目录、配置和采集数据。

此前 ChatGPT 附件修复已在用户浏览器完成实际下载验收：39 项失败中恢复或验证通过 33 项，本地去重附件从 178 增至 201。剩余 5 个历史源码链接当前返回 404（原网页抽查也下载失败），另 1 项是测试示例图片链接。该结果不代表所有来源永久可用，亦不替代可选 GitHub 数据备份的独立验收；详见 [验证记录](docs/validation.md)。

0.4.6 的“立即检查更新”仍会扫描全部列表，但完整、未变化且本地文件齐全的豆包对话会跳过正文请求。升级前已经创建的旧任务可点击“停止本轮”，再点击“立即检查更新”建立新队列，让增量跳过规则生效。

“暂停采集”保留旧队列，继续时接着处理。“停止本轮”结束当前对话队列并暂停当前账号的自动附件下载，定时器和浏览器重启不会自动续跑；重新开始后按配置恢复调度。已保存的正文、附件和待备份记录保留，已经开始的文件提交先安全完成。附件手动补齐和 GitHub 备份仍可独立使用。

空闲时，面板和页面入口的定时刷新复用已确认账号，不再每隔约 10 秒触发远程核验；后台空闲调度也复用该结果。首次识别、扩展后台重新启动、打开或重新聚焦面板、来源标签页切换或刷新时重新确认账号；采集到期、手动采集和附件处理仍保留必要校验，写入前再次检查账号归属。核验失败后，普通界面刷新复用错误状态，由页面事件、后台重试或手动操作重新核验。

## 使用流程

1. 打开并登录 ChatGPT（个人空间）或豆包网页端。
2. 点击扩展图标，按首次引导授权对应平台、确认账号名称、选择固定保存目录。
3. 保持“自动下载图片和附件到本地”开启。GitHub 步骤可以选择“稍后配置”；需要云备份时，填写自己的**私有数据仓库**及仅授权此仓库 Contents 读写权限的 Token，并明确选择对话自动上传及自动恢复。只连接仓库不会自动开启这些任务。
4. 完成引导并开始初始化采集。之后在对应平台页面边缘展开面板即可使用，GitHub 配置留在设置中。

| 方式 | 行为 |
| --- | --- |
| 初始化采集 | 首次遍历普通列表，读取详情并保存；未完成部分保留进度 |
| 定时增量 | 默认每 30 分钟检查新增、更新与待重试项；设置中可改为 15 / 30 / 60 分钟或关闭 |
| 立即检查更新 | 手动触发一次增量检查，无需等待定时任务 |
| 补齐缺失 | 分批检查本地归档；从已核对的 JSON 重建缺失 Markdown，将缺失或尚未下载的受支持附件安排为手动补采，仍需可访问来源；缺失 JSON 由后续采集补回 |
| 立即备份到 GitHub | 从本地归档建立对话上传任务；自动上传关闭时也可使用，无需重新向网站抓取全部对话 |
| 全量补采 | 重新遍历列表并读取详情，补齐缺失文件；同一对话更新原档，不重复建档 |
| 重试失败附件 | 先核对本地来源，移除误识别的工具图标和普通 GitHub 文档浏览页任务；其他失败附件刷新所在对话的线上详情并逐项补采，不重新扫描对话列表 |
| 尝试获取内部附件 | 手动重试已经停止自动获取的内部看图附件，每项尝试一次；仍未取得时继续明确标注缺失 |
| 从 GitHub 恢复对话 | 把已配置私有仓库中的对话归档恢复到本地，不要求来源平台登录；保留可重试进度 |

定时采集需要浏览器正在运行、可访问的已登录来源平台标签页和有效目录权限；已有本地数据的 GitHub 同步与恢复不依赖来源平台登录。浏览器退出、电脑休眠、登录失效时不保证执行或准点执行；恢复条件后补做检查。同一账号的手动和定时任务共用队列，收起面板不代表暂停任务。

旧版操作记录见 [0.2 使用指南](docs/v0.2-guide.md)；当前设置与行为以下文为准。

## 豆包接入（0.4.7）

沿用原扩展目录升级并重新加载，在豆包网页点击扩展图标。首次引导或设置中的“授权豆包”只申请 `www.doubao.com` 访问；识别账号后单独启用。已有 ChatGPT 账号、保存目录和开关继续保留。豆包档案位于 `data/web/doubao/<账号目录>/`。

- 普通对话列表采用版本游标分页；每条详情分页读取当前消息链，并在前后核对账号及会话版本。消息仍在生成、分页停滞或版本变化时保留已有归档并报告失败。
- JSON 保留豆包原生消息块与接口返回的重新生成记录，剔除获取令牌和遥测字段；Markdown 显示消息正文。历史分支、项目、归档对话、临时对话及未识别的非文本块不承诺完整覆盖。
- 已观察到上传图片的 `attachment_block → image_ori` 结构。先从原对话核对资源；结构化文件通过网页文件接口刷新签名地址，图片返回 403 时尝试同一原文件 URI 的新地址，再从 `*.byteimg.com` 匿名下载；在设置中单独点击“允许下载豆包原图”。单文件仍限 32 MiB；支持已识别文件类型（含 UTF-8 `.ps1`，只归档、不执行），其他文件和音视频暂不承诺下载，来源与未适配内容留在 JSON。
- 增量任务按列表版本、标题与本地文件判断是否需要重读；需要读取时获取整条消息链，不套用 ChatGPT 的尾部消息增量协议。
- GitHub 对话上传、恢复和本地 Markdown 修复沿用现有流程；恢复不会自动启用豆包账号，附件不上传 LFS。

实机已发现 222 条对话，并完成包含 642 条消息的长对话落盘。0.4.1 兼容消息字符串中的正文、图片实体及已终止的中断回复，旧豆包渲染版本会重新核对；自动化测试使用合成数据。后续实机核对已归档 222 条对话并全部使用当前豆包渲染版本；0.4.4 更新前有 351 个已下载附件、6 个待处理附件，0.4.4 重试后其中 4 项实际恢复并通过哈希和 Markdown 引用核验。0.4.5 将上限提高至 32 MiB 后，20.35 MiB 照片也已成功归档并与网页下载字节一致。现为 356 项已下载、1 项待处理，仅剩原网页也无法加载的 Redis 简图，验收状态见 [验证记录](docs/validation.md)。

## 本地保存与云备份设置

| 设置 | 新安装默认 | 行为 |
| --- | --- | --- |
| 自动检查对话更新 | 开，每 30 分钟 | 保存 JSON 并生成 Markdown；可改为 15 / 30 / 60 分钟或关闭 |
| 自动下载图片和附件到本地 | 开 | 下载受支持的真实附件，不依赖 GitHub；关闭后新下载显示“按设置暂停” |
| 自动备份对话到 GitHub | 关 | 自动上传 JSON、Markdown 及必要清单 |
| 自动从 GitHub 补齐本地备份 | 关，在高级设置中 | 独立控制远端恢复，不会因为开启上传而自动打开 |

JSON 与 Markdown 默认同时保存。关闭自动下载或云端任务会保留已有文件和未完成记录；重新开启后继续处理。手动补齐或重试可在附件自动下载关闭时安排一次尝试，服务器限流仍需等待。正在完成的本地文件写入会保留一致性检查和恢复记录。原目录有未完成的正文或附件写入时，更换目录会被阻止；先恢复权限并重试原写入，完成后再切换。

这组默认值只用于新安装。0.2–0.3.16 的现有配置升级时，原“自动同步并补齐本地备份”按旧选择分别迁移到自动上传和自动恢复；0.3.24 起忽略旧附件上传开关。配置仓库、对话上传或恢复设置后先点击“保存 GitHub 设置”，再执行“立即备份”。关闭自动上传和恢复时，不要求重新授予已撤销的网站权限。

未启用自动上传时，新本地采集仅记录必要的变更信息，不为每个新版本长期增加待上传正文副本；已经存在的有效待交付记录继续保留。以后启用上传或手动备份，会核对本地文件并分批建立任务，遇到手工改动时提示冲突。已有数据不需要为了连接仓库而重新全量抓取网站。

## 本地完整性与缺失补齐

“本地备份完整性”按对话列出正文状态、已识别附件总数，以及已保存、失败、仅外链、暂不支持、内部附件缺失和按设置暂停的数量。界面最多展示前 50 条并提示总数；这是当前采集范围内的记录，不代表账号所有历史、所有分支或所有资源都已取得。原生 JSON 保留已返回的结构，Markdown 展示可读的当前分支；只有当前分支数组时不能据此声称其他分支也已备份。

插件在浏览器运行且目录授权有效时，对启用账号约每 24 小时发起一次本地检查，分小批次执行并保存进度；不是固定时刻运行，也不会在电脑休眠期间执行。检查以文件存在性与大小为主，不反复读取全部历史正文。点击“补齐缺失”可提前发起一轮：

- 缺失 Markdown：先核对原始 JSON 的摘要和归属，再通过已有写入恢复流程生成。
- 已记录下载成功但实体已丢失的附件：撤销“本地已有”的判断并加入补采；实际下载仍取决于账号、权限和源文件是否可获取。
- 缺失 JSON：记录为正文待补采，正常增量或手动“立即检查更新”会尝试重新取得来源。
- 文件大小异常、JSON 不符或人工改动：保留文件并提示；存在但为空的文件不会被擅自当成可覆盖对象。

轻量检查不证明同大小文件的字节从未变化；修复、读取增量基线和上传时仍按相应流程核对摘要。公开外链默认只保留链接，不算附件实体已落盘；本版未新增外链全部下载或音视频支持。

## 增量采集的判断

“立即检查更新”和定时采集会分页读取轻量列表中的 ID、标题和更新时间，再决定哪些对话需要详情请求：

| 对话状态 | 本轮处理 |
| --- | --- |
| 新 ID、更新时间变化或标题变化 | 读取该对话详情并更新原档 |
| 已有完整归档，时间及标题相同，JSON / Markdown 均存在且非空 | 跳过详情，不重新写入对话文件 |
| 时间无法识别、归档完整度未确认或文件缺失 | 补采该对话 |
| 上轮读取、保存或加入上传队列尚未成功 | 保留补采义务，连续列表失败也不会将其忘记 |
| 手动“全量补采” | 强制重新读取全部可枚举的对话详情 |

跳过判断不再要求整个账号初始化全部成功，也不因对话处于最近 5 分钟而重复请求。GitHub 恢复后的完整归档可使用清单中的来源更新时间；浏览器索引只在内容哈希与当前清单一致时复用。秒、毫秒、数字字符串和 ISO 时间统一比较；详情若早于列表刚发现的版本则等待重试，不推进成功记录。

列表仍需分页核对，不能只依赖全局“最后同步时间”停止扫描，否则会漏掉较旧但尚未采集的 ID。先按**对话**筛选，再按下述规则读取详情。若平台修改内容却不改变时间和标题，普通列表筛选无法发现，可用“全量补采”复查；已经复用历史前缀的归档还有定期完整复查。日常列表检查只核对本地文件是否存在且非空，不重新计算全部历史正文的哈希。

更新前已经创建的未完成任务仍沿用原队列继续，避免中断文件交付；新筛选规则从下一轮新建检查生效。无需清空数据或重新绑定账号。

## 消息分页与尾部增量

分页读取当前分支的消息数组 `messages` 时，先读取最近一页，使用 `page_info.start_cursor` 作为 `before` 游标向前获取历史；顺序由服务器数组及游标关系决定，不按消息时间自行排序。每页检查 ID、首末游标、分页标记、生成状态及账号；需要拼接时还要求可靠的更新时间和当前节点，多页读取完成后再次核对最新页，发现版本变化则停止本次拼接或回退完整消息树。

| 已有归档 | 处理方式 |
| --- | --- |
| 完整 `messages` 数组，近期已完整核对 | 最新页与本地末尾至少 3 条连续消息的 ID 和脱敏后内容一致，且其后有新 ID，才复用此前的历史前缀 |
| 只遇到一个旧 ID、重叠消息变化、旧 ID 顺序异常或未找到本地末尾 | 继续向前分页，完整读取当前分支；分页不可靠时尝试完整消息树，失败保留原档 |
| 缺失、损坏或未经完整核对的本地归档 | 不作增量基线；缺失时完整补采，人工修改冲突需处理后继续 |
| 已有 `mapping` 消息树 | 继续完整读取消息树，保留历史分支；不会自动转成仅含当前分支的数组 |
| 首次采集或手动全量补采 | 完整读取；新对话优先完整消息树，接口不可用或结构不匹配时尝试完整数组分页 |

仅下载最新一页也会包含少量重叠消息，并非接口只返回“新增的两条”。比较使用与归档一致的脱敏规则，签名凭据变化不作为正文修改；正文、附件身份、状态及原生消息字段的变化仍参与判断。归档继续保存一组完整 JSON / Markdown，不拆成每条消息一个文件，也不伪造消息树节点。

复用前会核对本地 JSON 的哈希，保存尾部合并时再次核对基线版本，防止网络读取期间本地归档已被更新。清单中的 `messageSync` 记录完整读取时间、历史复用方式及消息计数；图片重写和 GitHub 恢复不会把旧历史标成刚刚全量核对。GitHub 冲突处理同样保护已有消息树。

尾部衔接只证明连接处一致，不能证明更早消息未被修改。距离上次完整读取达到 **7 天**或已完成 **20 次尾部增量**，下一轮正常检查会完整读取该对话，即使列表时间未变化也不跳过。它依赖浏览器和账号可用，不是独立常驻任务。手动“全量补采”随时强制完整读取。

当前仅对已有完整数组格式启用尾部增量；旧版数组缺少完整读取记录时先完整读取一次，已有消息树不会因为升级而自动改格式。网站私有分页接口仍需实际账号验收，不保证全部对话都能减少详情下载。

点击暂停、切换账号或源标签页失效时，会向采集器自己的网页请求发送取消信号，尽快停止详情和平台附件的网络读取；取消后的迟到结果不写入归档。已开始的本地文件写入会完成一致的保存与交付记录。继续采集时从当前对话的最新页重新读取，已经完成的其他对话保留。匿名外链检测是独立的短请求，当前保留 15 秒时限，不保证每种网络操作都能瞬间中止。

单次详情 HTTP 请求有 **10 分钟总时限**，覆盖响应头与正文读取，不随数据分块续期；前后账号核验及列表请求各有 20 秒时限。等待详情期间每 20 秒调用一次轻量扩展 API 临时维持后台运行，不记录其返回信息、不新增权限；整个脚本回执另设 11 分钟看门狗，给前后身份核验留出时间。成功、失败、超时后均停止临时保活，晚到回执不再归档。

超过时限显示 `TIMEOUT`，同轮暂时错误最多尝试 3 次，通常先等待 1 分钟、2 分钟；仍失败后保留跨轮次冷却记录。未完成响应不落盘。同账号的采集仍按顺序执行，不同账号可分别推进，长网络等待不占用全局文件写锁；恢复与目录切换仍需避开正在使用的文件。10 分钟不是整条长对话多页读取的总时长；电脑休眠、浏览器退出、页面关闭或扩展后台异常终止仍可能中断，不能保证所有慢请求都能完成。

完整消息树中，历史消息可能仍带有 `pending`、`streaming` 或 `in_progress` 状态。采集器只在**同一分支后续**存在 `assistant / finished_successfully / end_turn: true` 的结束消息时，将其作为历史状态原样归档；指向工具或分析通道的消息不作为结束证据。当前分支只能用当前分支的结束记录确认，当前节点或没有结束证据的旁支仍会阻止本次覆盖。不按对话年龄放行，不改写状态，不删除节点；缺页和树结构校验继续执行。消息数组及分页响应暂不使用此例外。

清单中的 `generationState` 记录历史未完成状态与无法确认结束的数量，每次从原生数据重算；Markdown 继续只展示对话。`sourceCompleteness: complete` 表示通过了本次返回结构检查，不表示每条消息都成功生成，也不保证平台全部历史均已取得。升级后可点击“继续采集”重试，无需清空数据。

## 查看运行进度

点击 **“采集详情”**、**“本地备份完整性”** 或 **“附件下载详情”** 可展开任务情况；启用云端任务后显示“下载与上传详情”。只用本地备份时隐藏无关的待上传提示；轮询刷新保留展开状态。

- 采集详情：当前正在核验账号、读取列表、读取哪条对话或保存文件，以及队列状态、错误代码和重试时间。
- 本条详情：消息页读取次数、接收消息数、复用历史数、新发现与修改数量；尾部增量明确标注“较早历史未重新核对”。接收数包含重叠及最新页复核，不能当作新增数量。
- 下载与上传详情：当前图片名称、下载／本地保存步骤、GitHub 对话提交和仓库恢复情况，区分本地附件保存与对话提交。
- 最近结果：保留每类操作最近 20 个步骤，展示最多 50 条队列明细，数量超过时会提示。日志只在本浏览器保存，不同步到数据仓库。
- 等待状态：按实际步骤开始与结束时间显示耗时；请求暂未有新进展、重试退避、采集暂停和上次处理被中断分别说明。计时不代表字节下载进度，也不把等待时间直接判为卡死。

详情采集出现 `INCOMPLETE_DETAIL` 时，展开失败项查看“原因”行和对话 ID。同名对话可以据此区分；原因会说明返回结果中的未完成消息、缺少的树节点引用，或无法核对的分页字段等具体条件。旧记录只有总错误码时，需要在升级后继续采集，才能取得新的原因；不要因此清空已有归档。错误诊断只记录固定原因代码，不记录对话正文、节点 ID、认证信息或原始响应。

采集队列中的 `INVALID_RESPONSE` 表示没有取得符合约定的页面采集结果，不等同于对话内容不完整。同轮首次失败后通常等待 1 分钟、第二次失败后等待 2 分钟，总计最多尝试 3 次；仍失败则进入跨轮次冷却，或按错误类型等待手动处理。新记录区分主页面结果缺失、脚本执行失败、空返回及返回格式异常。标签页已关闭或离开 ChatGPT 时优先暂停等待恢复；错误返回不会写入归档或推进成功索引。

手动同步等待期间仍刷新只读进度；后台读取迟迟未返回时会提示状态读取等待。重新核验标签页账号时会标明显示的是上次确认账号，核验期间暂禁账号相关操作。更新后的新操作才会产生这些步骤记录，旧历史不会补造。

## 重试与账号限流

失败记录按来源版本跨采集轮次保留，不因新一轮列表扫描就归零。网络暂时失败继续退避，重复失败进入较长冷却；格式或大小等需要适配的错误等待手动处理。对话版本变化、明确全量补采或手动继续可以重新尝试相应记录。附件按等待授权、来源恢复、格式适配、本地冲突分别展示，恢复来源或明确重试后再处理；404 不会作为删除本地归档的依据。

平台提供有效 `Retry-After` 时会读取秒数或日期并采用等待时间；429 触发账号级冷却，详情和附件请求共用该账号的等待条件。手动重试不会绕过尚未结束的账号冷却。现有“未变化跳过详情”与消息尾部复核继续保留；日常列表目前仍完整分页核对，“近期轻扫＋低频全列表核对”尚未实现。

## 附件与恢复

对话 JSON 继续保存平台原生结构；Markdown 展示对话正文、图片和附件链接。能取得的私有／临时附件保存为本地实体。GitHub 仅上传对话文件及清单，不上传附件、不生成指针、不读写附件跟踪规则。附件失败重试从原来源补采；链接和旧版指针不算本地文件已下载。

当前支持 ZIP、GZIP / TAR.GZ / TGZ、PDF、DOCX / XLSX / PPTX，以及 TXT、Markdown、CSV、TSV、JSON 和常见 UTF-8 源码文件，单文件上限仍为 **32 MiB**。ZIP 检查容器结构，Office 文件核对对应目录，PDF 检查头尾标识；登录页、错误网页和不符合预期格式的数据不会冒充附件保存。GZIP 通过有界解压验证帧、CRC 和完整性，校验后的内容同样不得超过 32 MiB；原始压缩包不变，不向磁盘提取或执行附件。其他格式不解压，也不保证源文件本身可正常使用。音频、视频、旧版 DOC / XLS / PPT、HTML 文件及其他未适配格式暂不承诺下载。

正文中的 `sandbox:/完整路径/文件.zip` 使用已观测到的 `/backend-api/conversation/<对话ID>/interpreter/download` 入口，参数固定为任务的 `message_id`、`sandbox_path` 与 `download_intent=true`。路径相同但来自不同消息的文件分开记录；不会按同名文件猜测对应关系。成功后 Markdown 使用本地相对链接；过期、无权限或无法取得的文件保留来源与待补采状态。普通网页引用不加入附件下载队列，公开下载链接保留在线引用，经可选匿名检测确认后仍保留为外链。

**旧对话补齐：** 升级后执行一次“全量补采”，让此前未识别的下载链接进入附件队列；日常增量仍会跳过时间及标题未变化的对话。已有文件会核验后复用，无需清空本地或 GitHub 数据。之后失败项可用“重试失败附件”单独处理。

普通对话图片失败时不需要清空数据。展开 **“查看失败原因”**，可看到对话标题、图片名称、错误代码与尝试次数；待处理数量包含失败项。点击 **“重试失败附件”**，会读取对应对话的最新图片来源信息，随后重试现有失败任务。即使对话采集已暂停或附件自动下载已关闭，也允许这次明确请求的图片补采，每项只尝试一次并遵守账号冷却；自动下载开启时，可自动重试的错误继续按分类和退避策略处理。图片已下载但归档入队失败时，只继续交付已有文件，不重复下载。

`asset_pointer_link` 有有效地址时可用于取图；只有 `sediment://` 或失效链接时，会结合归档任务中的文件 ID、对话 ID 尝试文件下载入口。内部接口或 Library 路径可能不适用，补采按钮不保证所有图片都能取得。诊断不会展示下载凭据、签名 URL 或服务器原始响应。

0.3.2 针对 Library 附件下载返回的浏览器不透明跳转，允许浏览器跟随指定的标准下载入口，随后验证最终地址与图片内容。Cookie 限于同源，跨源跳转的 Authorization 由浏览器按 Fetch 标准移除；此例外不用于任意外链或源数据中的其他 URL。

0.3.3 补齐实际观测到的同源 `/backend-api/estuary/content` 下载地址：要求唯一的查询参数 `id` 与当前附件的文件 ID 完全一致，继续核验图片字节和账号。签名地址只临时用于请求，不写进归档或诊断。这个规则用于接收平台返回的地址，不能仅凭文件 ID 构造可用的签名链接，也不代表所有 `ASSET_PENDING` 生成图片已能下载。

0.3.4 增加 `/backend-api/files/download/<文件ID>` 入口，使用任务归属的 `conversation_id`、`download_intent=false`、`inline=true` 获取图片来源。它不要求原图已在当前页面打开，也不使用当前标签页的对话 ID 替代任务归属。请求仍在已登录的同账号 ChatGPT 标签页执行；取得内容后检查原图大小、尺寸、类型、哈希及账号，随后保存本地。旧失败项可直接“重试失败附件”，无需全量重采。该入口已在真实网页资源清单中观测，扩展端到端下载仍需用户设备验收。

0.3.5 修正同一图片同时出现在上传附件与 AI 文件引用中的重复计数：只有直接文件引用明确提供文件 ID 与 Library ID 时才合并，保留全部消息来源。旧版多建的 Library 图片任务可在重试时按同账号、同对话的原始记录核对并纠正；原图片已经下载且本地字节验证通过时直接复用。GitHub 合并相同对话原文时应用同样的对应规则，避免旧重复记录重新出现。不能唯一确认对应关系的记录继续保留，不按同名文件猜测。工具运行中产生的附件可能使用另一文件 ID，不能因此判定为同一原图；仍需平台提供可访问的下载来源。

0.3.6 仅将原生消息中 `tool / container.open_image` 的 `execution_output` 附件识别为内部看图附件；同一图片只要还有普通消息引用，就仍按普通图片处理。内部附件也会先尝试下载，仅在下载返回 `HTTP_404` 时停止自动重试，并单独显示 **“内部附件未下载”**。这类记录不再计入普通图片失败数，但不算已下载或完整备份；原始 JSON、文件 ID、消息位置及错误代码继续保留。可点击 **“尝试获取内部附件”** 再试一次；成功取得字节后仍按原流程保存到本地。401、403、限流或网络失败不按 404 处理；其他工具、用户上传图片、回复展示图片及生成图片不会因文件名或路径相似而被忽略。

旧的 404 任务会在下一次图片任务处理时核对本地原始 JSON 并迁移；暂停采集时也可主动点击“重试失败附件”触发一次尝试。升级、重启、重采及相同原文的 GitHub 合并／恢复会保留经过来源核对的缺失状态，不根据同名或同大小的图片猜测替代关系。

公开外链图片和受支持的公开文件不默认复制到仓库。在设置中主动点击 **“允许检测外链附件”** 后，扩展才申请覆盖 HTTPS 网站的可选权限，并匿名检测外链图片及受支持文件是否可用；检测不携带 ChatGPT 或 GitHub 凭据。未授权或无法确认的外链保留链接及待处理状态。GitHub 授权不会顺带申请此权限。

在新电脑恢复对话：

1. 打开扩展设置。首次引导也可以直接点“已有备份？从 GitHub 恢复”，无需先绑定 ChatGPT。
2. 选择保存目录，填写私有仓库、分支和 Token，点“保存 GitHub 设置”。只手动恢复时可保持“自动备份对话到 GitHub”和“自动从 GitHub 补齐本地备份”关闭。
3. 点 **“从 GitHub 恢复对话”**，按提示授权 GitHub API。
4. 查看恢复进度；失败时点“重新尝试恢复”，重新检查仓库并补齐。恢复不会自动启用任何账号的采集，之后采集仍需核实并绑定当前登录账号。

只有“自动从 GitHub 补齐本地备份”开启时，才按设置间隔检查远端并补齐各账号的本地对话归档；手动恢复可独立执行。恢复只读取采集器识别的账号归档，不是通用 Git 客户端；不会因为远端缺失就删除本地文件。遇到本地手工修改、新旧版本无法判断、图片缺失或权限不足时保留状态，不强行覆盖。恢复只通过 GitHub API 读取对话文件；附件需从原电脑复制或绑定原来源平台账号后重新采集。

对话备份中的已保存附件标为 `cloudStatus: local-only`，GitHub 上的 Markdown 可能显示不出仅在本机的图片。新电脑恢复会报告缺少的本地附件，并保留从原来源补采的任务；没有来源账号授权时不会自动采集。旧版留在仓库中的附件指针、Git 属性文件和 LFS 对象保持原样，本版不再传输这些对象。迁移电脑时，请一并复制整个本地 `ai-memory-data` 目录；只有对话文件无法还原附件字节。

## 文件与账号

- JSON 保留平台返回的原生对话结构，结构化认证字段会脱敏；Markdown 从同一版本 JSON 自动生成，保留常见富文本与媒体引用，移除可执行 HTML。
- 按网页来源、平台、稳定账号目录隔离写入。目录使用账号标识的哈希，同一账号在不同设备保持一致；自定义名称保留在界面与 account.json，不以同名昵称判断归属。
- 文件名包含创建时间、标题和对话 ID；续聊、改标题或再次补采仍更新原文件路径。
- 本地先保存并核对，再同步到已启用的私有 GitHub 仓库。上传失败保留待同步数据，不显示为上传成功。
- 发现不完整或生成中的详情时保留原档；列表缺失、404 或请求失败不会触发删除。
- 本地人工改动、无法判定的新旧版本和远端竞争会保留数据并提示状态，不强制覆盖。多设备完整恢复仍需进一步验收。

示例目录：

```text
data/web/chatgpt/<稳定账号目录>/
  account.json
  archive/manifest.json
  assets/<附件内容哈希>.png
  assets/<附件内容哈希>.zip
  conversations/2026/10/
    2026-10-21T06-00-00Z__项目规划__<对话ID>.json
    2026-10-21T06-00-00Z__项目规划__<对话ID>.md
```

附件扩展名根据预期类型与实际内容核对；本地 `assets/` 保存文件字节，GitHub 不保存这些二进制文件。ZIP 下载仓库也不能补齐仅在本机的附件。

个人对话、Token、Cookie 和登录信息不进入本代码仓库。GitHub Token 只保存在当前浏览器扩展存储中，不传给 AI 网站，也不写入归档。启用 GitHub 同步后会上传**真实对话文件**，启用图片同步后还会上传已取得的私有图片，请使用自己的私有数据仓库。

## 安装与更新

首次安装：取得需要验证的代码版本并解压，在 `chrome://extensions` 或 `edge://extensions` 开启开发者模式，选择“加载已解压的扩展程序”，选中仓库内的 **extension** 文件夹。用户运行插件无需 Node、Python 或 Git。

已有用户请覆盖**原来加载的 extension 路径**，在扩展管理页点“重新加载”，再刷新已打开的来源平台页面。沿用同一浏览器配置和扩展身份，不卸载重装、不换目录，才能继续使用原扩展存储。

0.1.x 升级会沿用数据库和已保存的目录句柄，迁移仓库、分支及此前明确选择记住的 Token。旧 `p0-captures/` 文件与未保存副本保持原样；首次新版引导仍需确认账号和真实对话上传设置，不会因为曾做过 GitHub 合成文件测试就自动开启上传。

升级至 0.3.17 时沿用账号绑定、目录句柄、采集进度和已有云端选择。新的纯本地默认值不会关闭旧用户已启用的云备份，也不会为此前未启用的用户开启上传。浏览器不会自动授予新增域名权限；需要时保存 GitHub 设置或点击授权按钮。旧版尚未识别的附件仍需一次“全量补采”发现，本地“补齐缺失”只处理已有归档和记录，过期源文件不保证可以补回。

0.3.18 的 Markdown 修复不要求清空归档或重新读取全部对话。定期本地检查或“补齐缺失”会分批核对旧 JSON 和 Markdown 摘要后重新生成阅读文件；已经手动修改的文件保持原样并报告冲突。实体图片尚未下载时显示待补采，不能把占位理解成已经完成图片备份。旧失败记录仍显示原来的分类；执行一次重试后才能获得本版新增的响应诊断，不需要反复重试整批附件。

0.3.x 升级至 0.3.11 无需清空本地目录、GitHub 数据或扩展存储。原地覆盖代码并重新加载后，支持的消息数组归档会先建立或复用完整基线，再判断尾部增量；消息树继续保留原格式。已有任务可以继续，下一次详情失败会记录具体原因；之前已经标记失败的任务需点击“继续采集”重试。图片失败仍可单独重试。权限范围与数据库名称保持不变。如果本地目录显示“需要授权”，先点击“恢复保存权限”，待状态变为“自动保存”后继续。

Mac 用户可使用 [双击更新器](docs/macos-update.md)。**0.2 之前下载的旧更新器需要一次性替换为新版 `update-macos.command`**：旧脚本只识别带 P0 的扩展名称，新脚本同时接受旧名称和新版名称。保留原 extension 目录，不用卸载插件。更新器只读取 `main`，不会安装尚未合并的开发分支；更新后仍需在扩展管理页重新加载。当前没有浏览器商店版本。

## 当前范围与限制

- 接入 ChatGPT 与豆包普通对话列表；团队工作区、项目、归档与临时对话尚未完成接入验证。页面昵称和会话身份不代表工作区已验证。
- 网站内部接口不是稳定公开 API。ChatGPT 优先读取消息树，必要时尝试消息列表；豆包按原生消息链分页读取。缺少可靠分页结束标记、缺失节点或仍在生成时会提示待补采，不把截断内容当作完整归档。
- 支持常见栅格图片、ZIP、GZIP / TAR.GZ、PDF、Office 与常见文本附件，单文件上限 32 MiB。临时链接过期、权限变化或内部接口改动可能导致下载失败；音视频及未适配格式保留引用，不保证实体备份。
- GitHub 上传支持读取远端现状、处理提交竞争、保留冲突版本；恢复入口读取归档清单和对话文件，不恢复任意仓库文件或 Git 历史，也不绕过本地冲突。
- 恢复与采集都需要浏览器运行和有效目录授权；中断后保留进度。附件本地下载失败会单独保留待处理状态，不保证单次操作全部完成。
- Gemini、DeepSeek 等其他平台尚未接入。每个平台需要分别验证账号、列表、详情和消息格式。
- 本阶段只采集归档，不进行 AI 记忆提炼、跨平台注入、搜索展示或自动执行对话中的指令。

## 开发与检查

Node.js 22+，测试使用虚构数据和模拟浏览器/文件/GitHub 接口，不需要用户账号或 Token：

```sh
npm test
npm run check
npm run package
```

打包需要 Python 3，仅收录 `extension/`，输出到 `dist/`。更新器测试还需要 Bash、ZIP、unzip、shasum 等工具；Linux 测试会模拟 macOS 专有命令。CI 执行自动化测试、静态检查和打包。

开发说明见 [路线图](docs/roadmap.md)、[采集设计](docs/collection-design.md)、[验证记录](docs/validation.md)。[P0 指南](docs/p0-guide.md)保留用于旧版本回溯，不能作为当前版本操作说明。

本仓库暂未选择开源许可证；正式开放贡献和发布前补充。
